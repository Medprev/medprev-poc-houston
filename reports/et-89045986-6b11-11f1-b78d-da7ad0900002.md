## Root cause

`medprev-web-app-backend-graphql` throws a `GraphQLError` (a `NotFoundError` from `BlogApi.getBlogPostBySlug`, `infra/medprev-cms/datasources/blog.api.mjs:54`) whenever the `blogPostBySlug` resolver receives a slug that has been percent-encoded multiple times over (chains of hundreds of `%25` sequences). That string never matches a real CMS slug, so the datasource correctly 404s. The resolver's behavior itself looks correct — it's a handled "not found," not a crash. The open question is upstream: something outside this service (or a caching/regeneration step) is repeatedly re-applying percent-encoding to already-encoded slugs before the request reaches this resolver. I did not trace request origin (user-agent/referrer/caller) in this pass, so the exact upstream producer is **not yet determined**.

## Recommended action

Pull `user-agent`/`referrer` and calling service for a sample of `graphql.resolve blogPostBySlug` traces to identify what's re-encoding these slugs (likely a sitemap/cache regeneration step or a redirect/proxy hop that double-encodes on each bounce), and add a defensive loop-decode of the slug before the CMS lookup as a stop-gap so malformed links fail fast without unbounded string growth.
