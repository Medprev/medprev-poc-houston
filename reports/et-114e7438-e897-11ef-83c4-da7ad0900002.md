## Root cause

`GetOnlineProfessionalService.findBySlug` (medprev-rest-api) throws `ProfessionalNotFoundException` whenever `GET /online/professionals/find-by-slug/:slug` is called with a slug that doesn't match any professional record; the handler correctly catches it and returns HTTP 404. The call chain confirmed for this specific fingerprint: `medprev-web-app-backend-graphql` resolves a `professionalSlug` GraphQL query → its Apollo REST datasource calls the REST API by slug → REST API returns 404 → GraphQL layer wraps it as a handled `GraphQLError: 404: Not Found`. This is a legitimate, fully-handled "not found" path, not a crash. The specific slug sampled (`dr-lumimed-laboratorio-…`) reads like a lab/clinic identifier rather than an individual professional — **inference, not confirmed**: this may indicate stale or mismatched slugs being requested (e.g., cached listings, a sitemap, or a search index pointing at removed/renamed professional records), but the actual source of the outbound calls (which caller/job feeds `professionalSlug`) was not traced beyond the GraphQL resolver in this investigation. The issue's real anomaly isn't the exception itself but its `regressed: true` flag: Datadog auto-resolved it (`AUTO_RESOLVE_NAIVE`) on 2025-11-05 and it re-opened via `REGRESSION_VERSION_AWARE` on 2025-11-10 (and similarly on 2025-10-16) — consistent with a chronic, high-frequency handled error that outlives Datadog's naive quiet-period resolution rather than an actual regression in code behavior.
