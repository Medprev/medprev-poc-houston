## Root cause
A handled `NotFoundError` ("City not found") is thrown by `_CityApi.getCity` (`infra/medprev-cms/datasources/city.api.mjs:34`) inside `medprev-web-app-backend-graphql` whenever a GraphQL resolver for a location/city field is asked for a city ID that doesn't exist in the CMS datasource. Datadog surfaces it as a `GraphQLError` Error Tracking issue even though it's `handling: handled`, `is_crash: false` — i.e. it's the application's deliberate "not found" path, not a crash. It has been present since `2026-06-18` (`first_seen_version: 0cc61fcc`) and is still firing on the current deployed version (`last_seen_version: 808de0ff`), so it is not a new regression. What is **not** verified is *why* callers keep requesting cities absent from the CMS (stale references, bad client input, or an environment/data mismatch) — answering that requires inspecting the actual city identifier passed per-call, which was not queried here.

## Evidence
- Error is a handled `NotFoundError` thrown from `_CityApi.getCity`, not a crash — `mcp__claude_ai_Datadog__get_datadog_error_tracking_issue(issue_id="36dac142-6b14-11f1-b5c1-da7ad0900002")`: `is_crash: false`, `last_error.custom.error.handling: "handled"`.

- Failing call site is a GraphQL field resolution — same call, `last_error.custom.resource_name: "graphql.resolve location"`, `operation_name: "Internal"`.
- Issue-level impact count (`total_errors: 4371`) does not match the finding's own `observed_count` (27,114) — same call vs. the input finding JSON; the two use different, unconfirmed time windows (the `get_datadog_error_tracking_issue` tool takes no `from`/`to` params), so **do not** treat 4,371 as "errors in the last 24h" without checking the API's default window first.

## Recommended action
Confirm with the medprev-cms/GraphQL owners whether "city not found" should ever reach Error Tracking as an exception versus being returned as a normal GraphQL error/null field; if it should stay visible, add the requested city identifier as a log attribute on `_CityApi.getCity` so a follow-up investigation can tell stale-reference from bad-input from real data gaps.
