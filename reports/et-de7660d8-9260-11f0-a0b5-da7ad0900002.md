## Corpo da issue

### Descrição do incidente
Em `medprev-rest-api`, a rota `GET /clinic/appointments/report` verifica a existência do arquivo do relatório no S3 (`HeadObject`) antes de servi-lo; quando o arquivo ainda não existe, o serviço lança `FileNotFoundException` a partir de `getUrlForFilesService.generate` (`/usr/src/app/dist/modules/s3/services/get-url-for-files.service.js`), que é capturado e devolvido como HTTP 404 ao cliente. Esse fluxo é registrado no Datadog Error Tracking como um erro de aplicação, gerando ruído no monitoramento sem indicar falha real do sistema. Impacto observável: nenhum, para o usuário (recebe 404 corretamente); para o time, ruído recorrente no Error Tracking.

### Causa raiz
Ruído confirmado: 100% dos spans de erro correlacionados (`n=141` na janela do achado) são `error.handling:handled` com `http.status_code:404` no recurso `HeadObject S3`. O trace completo de uma ocorrência mostra o fluxo de negócio (checagem de existência de arquivo) terminando com resposta HTTP 404 controlada (`status:ok` no span raiz), sem exceção não tratada, sem erro 5xx e sem indício de regressão de deploy (versão `0198e66d` estável na janela). Não foi determinada a causa de por que o arquivo não está disponível no momento do request (ex.: geração assíncrona ainda em andamento, ou falha silenciosa da geração) — nenhum log de aplicação foi encontrado para essa rota na janela consultada.

### Ação recomendada
No repositório `Medprev/medprev-rest-api`, revisar `modules/s3/services/get-url-for-files.service.js` (`getUrlForFilesService.generate`) e o handler de `createReport` na rota `/clinic/appointments/report`: (1) confirmar se existe um job assíncrono que gera o arquivo antes do download e, se sim, medir o tempo entre a geração e a primeira tentativa de download do cliente para descartar condição de corrida; (2) se o comportamento "arquivo ainda não pronto" for esperado, parar de propagá-lo como exceção capturada pelo Error Tracking (retornar 404 sem lançar `FileNotFoundException`, ou marcar essa exceção especificamente como esperada/ignorada na configuração do Error Tracking) para eliminar o ruído; (3) adicionar um log estruturado nesse caminho (hoje ausente, confirmado pela consulta de logs vazia) para permitir diferenciar "não gerado ainda" de "falha real de geração" em investigações futuras. Validar rodando `mise run investigate` ou observando o Error Tracking após a mudança: o volume de `FileNotFoundException` para essa rota deve cair a zero sem novos 5xx.
