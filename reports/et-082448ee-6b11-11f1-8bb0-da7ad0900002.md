## Root cause
The `blogReviewer` field resolver on `blogPostBySlug` calls `ProfessionalApi.professionalById()`, which does a REST lookup against the professional-service API via Apollo's `RESTDataSource`. When that lookup returns HTTP 404 (the professional/reviewer ID referenced by a blog post does not exist in the professional service), `RESTDataSource` throws a `GraphQLError: 404: Not Found`, which propagates up as a field-level GraphQL error rather than crashing the request (`error.handling: handled`, `is_crash: false`). This is data-integrity fallout, not a code crash: some blog posts hold a `reviewer`/professional reference that is stale or invalid, and every request that resolves that field re-triggers the failed lookup.

## Evidence
- Exact error, stack trace, and resolver chain (`ProfessionalApi.professionalById` → `blog-reviewer.resolver.mjs` → `blogPostBySlug.blogReviewer`) confirmed via `get_datadog_error_tracking_issue(issue_id: 082448ee-6b11-11f1-8bb0-da7ad0900002)`.
- Error is marked `handling: handled`, `is_crash: false`, `type: custom`, `source: apm` in the same issue payload — confirms it's a caught, per-field GraphQL error, not a service outage.
- First occurrence 2026-06-18T12:26:56Z at git `0cc61fcc`, still occurring as of 2026-09-01T19:50:01Z at git `808de0ff` (`first_seen`/`last_seen_version` fields on the same issue) — the bug predates and survives at least one deploy, i.e., it isn't tied to a single bad release.
- Daily volume is high and worsening, not flat: `analyze_datadog_error_tracking_errors` filtered on `issue.id:082448ee-6b11-11f1-8bb0-da7ad0900002` over the last 14 days shows 2,886–10,349 errors/day, versus the ~343/day implied by the finding's 26,065-count average over its full ~76-day life — recent days are running well above the historical average.
- **Not verified**: whether this is one blog post with a stale reviewer being hit repeatedly (traffic amplification) or many distinct posts each with a broken reference (broad data drift). The error-sample payload doesn't carry the blog post slug or professional ID as a queryable attribute in the default `errors` schema, so this wasn't checked — flagging rather than guessing.

## Recommended action
Query the professional-service/CMS data to find which blog post(s) and professional ID(s) are driving the 404s (join blog `reviewer` references against the professional service, or add `blog.slug`/`professional.id` as logged custom attributes to make this queryable in Datadog), then either backfill/clear the stale reference or make `professionalById` return `null` for a 404 instead of throwing, so a missing reviewer degrades gracefully instead of erroring on every request.
